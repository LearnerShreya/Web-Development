Number Representation in Different Formats

Here we describe how a single number can be represented in different formats: decimal, binary, and normalized binary. Let's take the example of the number 42.75.

1. Decimal Form

This is the standard base-10 representation of the number. Humans typically use this format in everyday calculations.

Number: 42.75

2. Binary Form (Standard Binary)

In binary, numbers are represented in base-2 using only 0s and 1s. The given number 42.75 is represented as follows:

Binary Representation: 101010.11

  • Integer Part (42): Converts to 101010 in binary.
  • Fractional Part (0.75): Converts to .11 in binary.

Explanation of Fractional Part:

  • 0.75 = 0.5 + 0.25
  • In binary: 0.5 = 2^-1 and 0.25 = 2^-2
  • Hence, 0.75 is .11 in binary.

3. Normalized Binary Form

To store the number efficiently, it is converted into normalized scientific notation in binary.

Normalized Representation: 1.0101011 × 2^5

  • The binary point is shifted 5 places to the left to make the number in the form 1.xxxxx.
  • The exponent 5 indicates the number of places the point was shifted.

Summary

The number 42.75 has three equivalent representations:

  1. Decimal Form: 42.75
  2. Binary Form: 101010.11
  3. Normalized Binary Form: 1.0101011 × 2^5

These formats serve different purposes. The decimal format is human-friendly, the binary format shows the number's binary structure, and the normalized binary format is used for efficient storage and processing in computers.

Understanding 64-Bit Numbers in JavaScript

JavaScript stores numbers using the IEEE 754 64-bit floating-point standard, enabling representation of both large and small values with precision. This format is used for all numbers in JavaScript, including integers and decimals.

Structure of a 64-bit Floating-Point Number

A 64-bit floating-point number consists of three components:

  • Sign (1 bit): Indicates whether the number is positive (0) or negative (1).
  • Exponent (11 bits): Encodes the range of the number using a "biased" format.
  • Mantissa (52 bits): Represents the significant digits of the number (excluding the leading implicit 1).
[ Sign (1 bit) | Exponent (11 bits) | Mantissa (52 bits) ]

The Concept of Biased Exponent

The exponent is stored in a biased format to make all its values non-negative, simplifying computation. For a 64-bit floating-point number:

  • Bias = 2k-1 - 1 = 210 - 1 = 1023
  • Stored Exponent = Actual Exponent + Bias

Steps for Storing a Number

  1. Convert the number to binary.
  2. Normalize it to scientific notation (e.g., 1.Mantissa × 2Exponent).
  3. Calculate the biased exponent (add 1023 to the actual exponent).
  4. Fill the Sign, Exponent, and Mantissa fields.

Examples

Example 1: Storing the Number 42

  • Binary Conversion: 42 in binary is 101010.
  • Normalize: 1.01010 × 25.
  • Biased Exponent: 5 + 1023 = 1028 (binary: 10000000100).
  • Fields: 
    Sign: 0 (positive)
Exponent: 10000000100
Mantissa: 010100000000...

Example 2: Storing the Number 0.1

  • Binary Conversion: 0.1 = 0.0001100110011... (repeating).
  • Normalize: 1.100110011... × 2-4.
  • Biased Exponent: -4 + 1023 = 1019 (binary: 01111110101).
  • Fields: 
    Sign: 0 (positive)
Exponent: 01111110101
Mantissa: 100110011001100...

Limitations of 64-Bit Numbers in JavaScript

1. Rounding Errors

JavaScript uses the IEEE 754 64-bit floating-point format, which cannot precisely represent all decimal numbers. Some fractions, like 0.1, cannot be accurately represented in binary, leading to rounding errors.

Example: Let's take the number 0.1, which cannot be exactly represented in binary. When you try to store this number, JavaScript approximates it to the closest possible value, causing minor rounding errors.

    0.1 in binary is a repeating fraction: 
    0.1 = 0.00011001100110011... (repeating)
    In JavaScript, it's stored as approximately 0.10000000000000000555, causing a small rounding error.

This error is typically very small but can accumulate in calculations that involve many decimal places, affecting the accuracy of results.

2. Floating-Point Arithmetic Example: 0.2 + 0.3

A commonly observed rounding error is the sum of 0.2 + 0.3. In an ideal world, the result should be 0.5, but due to the limitations of floating-point representation in JavaScript, the result may be slightly different.

    0.2 + 0.3 = 0.5000000000000001 (not exactly 0.5)

This happens because the binary representation of 0.2 and 0.3 is not exact, and their sum produces a result that is a small bit off from the expected value of 0.5. While this difference is typically minuscule, it can cause problems in calculations requiring high precision.

3. Large Integer Precision

JavaScript uses a 64-bit floating-point representation for all numbers. While this allows for a large range of values, it sacrifices precision for very large integers beyond 253 - 1 (approximately 9 quadrillion). For integers larger than this, JavaScript starts losing precision and cannot represent them exactly.

Example: For integers larger than 253 - 1, such as 9,007,199,254,740,991 (253), JavaScript can no longer store them accurately:

    JavaScript can store up to:
    9007199254740991  (accurate)
    9007199254740992  (rounded)

After reaching this point, any larger integer will lose precision when stored or manipulated, leading to inaccurate results for operations involving large numbers.

Applications and Challenges of 64-Bit Numbers

1. Financial Calculations

In financial calculations, accuracy is crucial, especially when dealing with currency, interest rates, or large sums of money. The rounding errors inherent in floating-point arithmetic can lead to significant discrepancies over time.

Example: Imagine you are calculating interest on a large investment for a long period of time, and small rounding errors accumulate in each calculation. These errors can lead to slightly inaccurate final amounts, which might cause serious issues in real-world financial systems. In such cases, using integer-based or fixed-point arithmetic (e.g., using BigInt or external libraries) can help avoid these issues.

2. Cryptography and Large Numbers

Cryptography relies heavily on working with large prime numbers and performing complex mathematical operations on them. The precision limitations of JavaScript's native number type can hinder such operations, especially when numbers are large enough to exceed 53-bit precision.

Example: When generating keys for encryption or performing large number operations like modular arithmetic, precision loss could break the cryptographic algorithm, making it insecure. JavaScript provides a solution with BigInt, a special type for handling arbitrarily large integers accurately.

3. Game Development

In game development, precise calculations are often required for physics engines (e.g., for simulating gravity, velocity, or collisions). Small precision errors can cause noticeable issues in gameplay, such as objects jittering or behaving unexpectedly.

Example: When calculating the trajectory of a projectile in a game, small floating-point errors could result in the projectile moving slightly off course or having an incorrect landing point. In such cases, game developers may use custom numerical methods or higher precision types like BigInt or other libraries to handle large and precise values.

Key Takeaways

  • JavaScript uses the IEEE 754 64-bit floating-point format to represent numbers.
  • While efficient, this format introduces rounding errors for decimal values like 0.1 and limits precision for large integers beyond 253 - 1.
  • In applications like financial calculations, cryptography, and game development, these limitations can cause significant challenges.
  • For tasks requiring precise large number handling, JavaScript provides BigInt for arbitrary-precision integers.

Summary of Key Challenges

  • Rounding Errors: Minor inaccuracies can accumulate, especially with floating-point numbers that cannot be precisely represented in binary. This is illustrated by the 0.2 + 0.3 example where the result is not exactly 0.5 due to floating-point imprecision.
  • Large Integer Precision: Numbers larger than 253 - 1 lose precision, making them unreliable for some use cases.
  • Applications: Financial systems, cryptography, and game development need to account for precision limitations when using JavaScript numbers.
